## 2. 来源逐条分析

### 来源 1：freestylefly/wechat-cli
- **链接**：https://github.com/freestylefly/wechat-cli
- **核实要点**：只读、SQLCipher 即时解密、默认 JSON 输出、11 个命令、支持 `history --limit --format json`；
  npm 包名 `@canghe_ai/wechat-cli`，pip 包 `wechat-cli`。
- **核心思想**：把本地微信数据库变成 Agent 可直接调用的命令行工具，数据不出本机。
- **直接复用（adopted）**：只读原则、JSON-first 输出、`history`/`members` 的命令语义与参数命名。
- **去掉（removed）**：不在核心代码中硬编码对该 CLI 的依赖，也不复制其解密实现。
- **重构/新增（improved）**：新增 `wcm/bridge.py` 适配层，把 `time/text/id` 等异构字段归一为
  统一 Message schema。L2–L4 完全不知道数据来自哪个工具——换数据源只改一个文件。
- **证据**：`wcm/bridge.py::read_cli`、`SETUP.md` §3。

### 来源 2：sjzar/chatlog
- **链接**：https://github.com/sjzar/chatlog
- **核实要点**：HTTP API（默认 127.0.0.1:5030）+ MCP SSE，支持微信 3.x/4.0，TUI 降低门槛。
- **核心思想**：把聊天数据访问做成服务，任何 AI 助手通过 HTTP/MCP 消费。
- **直接复用（adopted）**："数据访问与业务分析解耦"的分层思想。
- **去掉（removed）**：TUI 与常驻 HTTP 服务——引入运维成本，与零依赖约束冲突。
- **重构/新增（improved）**：把 HTTP API 写成 `cli` 适配器的备选实现说明，
  使 transport 可替换；上层模块接口不变。
- **证据**：`docs/architecture.md` §3、`SETUP.md` §3.3。

### 来源 3：Agent Skills 开放规范（agentskills.io）
- **链接**：https://agentskills.io/specification
- **核实要点**：一个 skill 是含 `SKILL.md` 的目录；frontmatter 必填 `name`（小写连字符、
  与目录同名）和 `description`（做什么 + 何时用）；渐进式披露。
- **核心思想**：把领域知识打包成 Agent 按需加载的文件夹，而不是塞进每次对话。
- **直接复用（adopted）**：frontmatter 规范、目录结构、渐进式披露。
- **去掉（removed）**：通用示例里的营销式描述和无关 license 样板。
- **重构/新增（improved）**：为每个 skill 增加 **Inputs / Outputs / Edge cases / Run** 四段契约，
  并附一个可直接执行的 `.py` 入口——让 skill 不只是说明文档，还是可运行工具。
- **证据**：`skills/` 下 6 个 `SKILL.md`。

### 来源 4：Neo4j Property Graph 模型
- **链接**：https://neo4j.com/docs/
- **核实要点**：节点 + 边 + 属性，关系本身携带语义，适合表达 SENT / SUBMITTED / MENTORED。
- **核心思想**：领域关系是一等公民，不应被压平进关系表。
- **直接复用（adopted）**：节点类型（Student、Challenge、Submission、Message、QAPair）与
  边类型（SENT、TAGGED_WITH、SUBMITTED、ASKED、ANSWERED、MENTORED）的建模方式。
- **去掉（removed）**：Neo4j 服务、Cypher、驱动依赖。
- **重构/新增（improved）**：用 SQLite 两张表实现同构 `PropertyGraph`：
  `nodes(id,label,props)` + `edges(src,dst,label,props)`，提供 upsert/邻域/统计接口。
  保留可替换后端——需要原生图查询时换 Neo4j 不改上层。
- **证据**：`wcm/graph.py`、`outputs/class_graph.sqlite`（244 节点 / 401 边）。

### 来源 5：SQLite FTS5
- **链接**：https://www.sqlite.org/fts5.html
- **核实要点**：SQLite 内建全文索引虚拟表，无需外部搜索服务。
- **核心思想**：检索能力可以内建在存储层，而不是外挂一个搜索引擎。
- **直接复用（adopted）**：把"检索内建"作为未来方向写入架构文档。
- **去掉（removed）**：v1 **不引入** FTS5 虚拟表。
  原因：在闭环尚未验证前先加索引层属于复杂度前置；当前关键词匹配已能通过验收。
- **重构/新增（improved）**：用 `challenge_linker` 的关键词 + 扩展名匹配先跑通；
  FTS5 列为 W5 候选，要求与现有方案做 A/B（准确率、检索耗时）后再决定。
- **证据**：`wcm/analyze.py::link_challenge`、`docs/architecture.md` §7。

### 来源 6：KSTAR 认知循环（课程材料）
- **来源**：课程包《真实项目执行方案0511.pdf》《C8.pdf》《CHALLENGE.md》
- **核心思想**：K→S→T→Â→R̂，用预期与实际的差值作为学习信号。
- **直接复用（adopted）**：五段结构、R̂ 必须可验证的原则。
- **去掉（removed）**："只写收获不写差距"的汇报式 AAR 写法。
- **重构/新增（improved）**：把 ΔR = R̂ − R 做成 AAR 的必填字段，
  并新增"不是根本原因但看起来像的"一栏，防止把环境约束误判为能力问题。
  Level 与 KSTAR 对应关系写入架构文档。
- **证据**：`02_执行阶段/W1..W4/*AAR*.md`、`docs/architecture.md` §4。

### 来源 7：Wechaty（双向通道）
- **链接**：https://wechaty.js.org/
- **核心思想**：通过协议层实现群消息读写与自动回复。
- **直接复用（adopted）**：只复用"Nudge Skill 在架构中的位置"这一设计概念。
- **去掉（removed）**：**整个写回能力在 v1 去掉**。
  原因：自动发消息涉及账号风险与误伤真实同学；只读闭环已覆盖绝大部分价值。
- **重构/新增（improved）**：保留接口设计位置，等有了合规确认与人工确认机制再实现。
- **证据**：`docs/architecture.md` §5、`outputs/verification_report.md` 已知局限第 3 条。

## 3. 创造性组合：三个张力的裁决

| 张力 | A 方案 | B 方案 | 我的裁决 | 理由 |
|---|---|---|---|---|
| 数据接入 | wechat-cli（CLI-first） | chatlog（HTTP/MCP） | 双适配器，默认 CLI | 把差异收敛到 `bridge.py`，既零服务又保留升级路径 |
| 图存储 | Neo4j（原生图语义） | SQLite（便携） | 图模型 + SQLite 实现 | 保留领域抽象，换取"单文件可直接验收" |
| 意图分类 | 规则引擎（可解释） | LLM（灵活） | 规则先行 + 可插拔 LLM 接口 | 成本/延迟可控、结果可复现；代价是同源标注导致准确率上界偏高，已如实披露 |

**组合结果**：一个不依赖服务、可离线复现、可被 6 种 Agent 调用、自带 18 项自动验收的系统。
单一来源都不具备这个完整形态——这就是"拿来"之后的重构价值。
