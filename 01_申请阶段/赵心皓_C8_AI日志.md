## 0. 工作流设计（先设计流程，再开始写）

| 阶段 | 我做什么 | AI 做什么 | 交接物 |
|---|---|---|---|
| ① 需求抽取 | 读完 8 份材料，确定真实项目边界 | 对 3 份 PDF 做文字提取与要点归纳 | 需求清单 |
| ② 领域建模 | 决定节点/边与消息 schema | 提出 3 套 schema 候选并说明取舍 | `core.py` / `architecture.md` |
| ③ 代码生成 | 逐模块审阅、运行、修 bug | 生成模块骨架与规则词表 | `wcm/*.py` |
| ④ 验证 | 写验收项、跑测试、看真实输出 | 起草验收项与测试骨架 | `verify.py` / `tests/` |
| ⑤ 文档 | 判断哪些内容该写、哪些该删 | 按结构起草 proposal / AAR 初稿 | 四类核心文档 |
| ⑥ 一致性校验 | 对照 rubric 逐项检查 | 辅助定位命名/数字不一致 | 交付包 |

**分工原则**：AI 负责"生成候选与结构化表达"，我负责"定义需求、做取舍、验证真实性"。
所有关键数字都从 `outputs/` 实读，不从 AI 输出里抄。

## 1. Proposal 写作的 5 轮 prompt 迭代

### Round 1 — 过宽指令（失败）

**Prompt：**
```
帮我写一个 C8 项目 proposal。
```

**AI 输出的问题：**
- 选了"Project A 教育落地"，理由是"我对教育很感兴趣"——典型的泛泛而谈；
- 没有引用任何 C1–C7 的具体产出；
- 拿来主义部分写了"参考了一些开源项目"但没有链接；
- 执行计划只有"第一周调研、第二周开发"。

**我的判断**：不合格。挑战明确写着"不要泛泛而谈，用你在 C1–C7 中的具体产出来证明"。

---

### Round 2 — 加角色、加证据约束

**Prompt：**
```
你的角色是 Elite20 学员，正在申请 C8 的 Project B 方向。
请按 5 部分结构写 proposal：项目选择、拿来主义分析、KSTAR 执行方案、
我的角色、早期验证。要求：
1) 项目选择必须逐条对应 C1-C7 的具体产出，禁止使用"感兴趣"这类表述；
2) 必须定义主角色和明确的"不负责什么"；
3) KSTAR 的 R̂ 必须是可验证的数字。
```

**AI 输出的问题：**
- 第 1、4 部分可用；
- 拿来主义仍只有 2 个来源，且没有 adopted/removed/improved 拆解；
- R̂ 写成"完成系统开发"这类不可验证描述；
- 我把项目理解为抽象的"企业本体系统"，但材料包其实有一个更具体的真实需求。

**我的修改动作**：重新读《C8 WeChat Class Management Challenge.pdf》，
确认这是导师给定的真实子任务，其技术内核（Property Graph / KSTAR / Agent Skill）与 B 同源，
于是把项目锁定为"微信群 → 班级管理 Agent 子系统"。

---

### Round 3 — 强制来源对比与取舍（关键一轮）

**Prompt：**
```
重写第 2 部分。要求：
- 列 7 个真实来源，每个给出可访问链接和核心思想；
- 每个来源必须拆成三列：直接复用 / 去掉 / 重构新增，去掉和新增都要写原因；
- 增加一段"来源之间的张力与我的组合决策"，至少覆盖：
  wechat-cli vs chatlog、Neo4j vs SQLite、规则引擎 vs LLM；
- 对 Wechaty 写回能力，明确写"去掉"以及风险理由，不要为了炫技保留。
另外，第 3 部分 R̂ 按周给数字，例如"W2：准确率>70%、≥5 提交、≥10 QA"。
```

**AI 输出的问题：**
- 7 个来源基本合格，但 FTS5 的"去掉"理由写成"性能不好"——这是编造的，我改为
  "v1 暂不引入，避免复杂度前置于验证，列为 W5 候选需 A/B 对比"；
- 把"规则引擎 vs LLM"写成了"LLM 一定更好"，与我实际采用的方案相反，我做了纠正；
- R̂ 数字仍偏乐观但已可验证，我按实际能力下调到与后续 AAR 可比的水平。

**我的修改动作**：逐条核对 7 个链接的可达性（用检索工具确认 wechat-cli、chatlog、
agentskills.io 规范真实存在），把"性能不好"这类无证据断言全部替换成有理由的取舍。

---

### Round 4 — 引入早期验证物一致性

**Prompt：**
```
现在系统已经跑通。请把 Proposal 第 5 部分改写为"早期验证"，要求：
- 只使用从 outputs/ 实读的数字，不要写预期值；
- 列出至少 5 类验证物：可运行代码、数据产物、自动验收、测试、实测指标；
- 用一段诚实声明写清楚与真实项目的差距（数据源是脱敏样本、分类器准确率是内部上界、
  没有写回能力），禁止把差距包装成已完成。
```

**AI 输出的问题：**
- 第一版把 96.4% 写成"模型准确率"，我改为"规则分类器在同源标注集上的准确率"，
  避免误导为外部效度；
- 第一版把"18/18 APPROVE"写成"全部需求已满足"，我改为"脱敏数据上端到端验收通过"。

**我的修改动作**：在 demo 与 proposal 中统一"真实约束"表述。

---

### Round 5 — 一致性校验

**Prompt：**
```
对照 rubric.json 五个维度（delivery 25 / problemSolving 20 /
artifactCompleteness 15 / aiUsage 20 / reflectionQuality 20）和 red_flags，
逐项检查我的 proposal + demo + AI日志 + 拿来说明，指出仍然缺失或自相矛盾的地方。
特别检查：R̂ 数字是否与 4 份 AAR 的 R 可比；文件命名是否符合 姓名_C8_*.md。
```

**AI 输出：**
- 发现 Proposal 中 W4 的 R̂ 写"≥17 项验收通过"，而 AAR 中实际为 18 项——一致（实际 ≥ 预期）；
- 发现 W3 R̂ 写"≥20 学生 × 8 挑战"，AAR 实际 24 × 8——一致；
- 提醒文件名中的"姓名"是占位符，需提交前替换；我保留占位并在 README 中显式提示。

## 2. 系统构建中的 AI 协作（错误与纠正）

| # | 我给出的指令意图 | AI 生成的问题 | 我如何发现 | 纠正方式 |
|---|---|---|---|---|
| 1 | "把消息模型写成 dataclass，输出统一 schema" | 输出用了扁平字段 `sender_wechat_id`，而验收要求嵌套 `sender{wechat_id,nickname}` | `verify.py` 的 L1-2 检查报 FAIL（17/18 → REJECT） | 修改 `Message.to_dict()` 输出嵌套结构，重跑后 18/18 |
| 2 | "按 QA 对给学生加答疑计数" | 把助教也计入了学生画像，出现 13 名学生（实际 12→24） | 打印 `student_profiles.json` 名单发现"助教-李老师" | 在画像循环中过滤 staff 前缀 |
| 3 | "生成分类器规则词表" | 词表与标注集由同一人设计，准确率虚高 | 我主动质疑 97% 的真实性 | 在验收报告与 AAR 中标注"内部上界"，并列入留出集计划 |
| 4 | "生成 18 项验收检查" | 部分检查只验证文件存在，不验证内容 | 我逐条审阅 criterion 字段 | 加入 schema 字段检查、checkpoint 二次运行检查、测试进程返回值检查 |
| 5 | "生成 6 个 SKILL.md" | 初始只有描述，没有 IO 契约 | 对照 agentskills.io 规范与项目需求 | 每个 skill 补 Inputs/Outputs/Edge cases/Run 四段 |

## 3. prompt 优化模式总结（可迁移经验）

1. **先给角色和用途，再给结构**：只说"写 proposal"会得到作文；说"你是申请 B 方向的学员，按 5 部分写，R̂ 要可验证"才得到可用稿。
2. **用反例约束比用正例更有效**："禁止使用'我很感兴趣'"比"要写得具体"有效得多。
3. **要求 AI 输出来源时，必须同时要求链接与取舍原因**：否则会生成"参考了一些资料"这种空话。
4. **让 AI 做一致性检查，但不要让它做事实判定**：它能发现"数字不一致"，但"链接是否真实""准确率是否外部有效"必须我自己核实。
5. **保留失败轮次**：Red flag "one_shot_ai" 的反向证据不是写"我用了 AI"，而是展示第 1 轮有多差、第 3 轮改了什么。
