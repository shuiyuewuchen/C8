# Weekly AAR — Week 3：Property Graph 与 Skill 封装

## 预期（R̂）

- Property Graph 能存储 ≥20 学生 × 8 挑战的数据；
- 6 个标准 SKILL.md，每个可独立运行；
- 自然语言查询能回答 ≥5 类不同问题。

## 实际（R）

- 图存储 **24 学生 × 8 挑战**，244 节点 / 401 边；
- **6 个** Skill 目录，每个含 SKILL.md + 可执行脚本；
- 自然语言查询 **6 类**全部返回实质答案；
- 学生画像 24 份，只含聚合量。

## 差值（ΔR = R̂ − R）

| 指标 | R̂ | R | ΔR（相对误差） |
|---|---:|---:|---:|
| 学生数 | 20 | 24 | +20% |
| 挑战数 | 8 | 8 | 0% |
| Skill 数 | 6 | 6 | 0% |
| 查询类型 | 5 | 6 | +20% |

综合相对误差约 **20%**，较 W1 的 40%、W2 的 37.7% 明显收敛。

- **完成了什么**：图模型、画像、Skill 规范、查询路由全部交付且可独立验证。
- **没完成什么**：`challenge-linker` 仍未拆成单独 Skill（W2 遗留），
  目前作为 `msg-classifier` 内部函数存在；我决定接受这一偏差并在架构文档中说明，
  因为它没有独立的调用场景。
- **意外发现**：第一次跑画像时出现了 **13 名学生**（应为 12，后来扩到 24）。
  名单里赫然是"助教-李老师"。

## 失败分析

- **哪里失败了**：学生画像把助教计入了学生集合。
- **根本原因**：`build_profiles()` 的主循环过滤了 staff，
  但随后按 QA 对累加答疑数的循环**没有过滤**，于是 `stats[qa.answerer]` 为助教凭空建了一条记录。
  这是典型的"两个更新路径只有一条做了过滤"。
- **不是根本原因但看起来像的**：
  - "样本数据里有假学生"——不是，样本中 staff 身份字段是正确的；
  - "分类器把助教标成了学生"——不是，意图分类没问题；
  - "emoji/昵称解析错误"——无关。
- **纠正动作**：在 QA 累加循环中加入 staff/助教前缀过滤，重跑后画像数从 25 → 24，
  与群配置一致。这个 bug 也说明：**聚合类代码的每个写入路径都要单独检查过滤条件**。

## 本周我发现了____，它比我之前的方案更好，因为____

本周我发现了 **agentskills.io 的 SKILL.md 开放规范**（https://agentskills.io/specification），
它比我之前自造的"skill 描述格式"更好，因为：
① 它是跨 Agent 的开放标准（Claude Code / Codex / Cursor 等均支持），
   不是只能在本项目里用的私有约定；
② frontmatter 的 name + description 让 Agent 能渐进式加载，
   不需要把 6 个 skill 的全部说明塞进上下文；
③ 规范本身要求"说明做什么和何时用"，
   倒逼我把每个 Skill 的触发条件写清楚，这直接提升了可复用性。

据此次发现，我把所有 skill 描述**替换为规范格式**，并新增 IO 契约章节——
这是一次真实的方案替换。
