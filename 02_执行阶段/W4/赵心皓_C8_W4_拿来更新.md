# 赵心皓_C8_W4_拿来更新.md

## 本周评估的来源：SQLite FTS5 官方文档

- **链接**：https://www.sqlite.org/fts5.html
- **核心思想**：在 SQLite 内建全文索引虚拟表，支持前缀、短语、BM25 排序，无需外部搜索服务。
- **检索动机**：W2 的 `challenge_linker` 靠关键词匹配，遇到同义表达（"交作业"vs"提交"）
  可能漏关联；FTS5 看起来是自然升级。

## 采用 / 丢弃 / 重构

- **采用**：把"检索内建在存储层"作为架构演进方向写入 `docs/architecture.md` §7。
- **丢弃**：v1 引入 FTS5 虚拟表。
- **重构**：保留现有关键词匹配作为基线，把 FTS5 列为 W5 候选，
  并要求做 A/B 对比（准确率 + 单次检索耗时）后才允许替换。

## 为什么评估后维持原方案

1. 当前只有 168 条消息、8 个挑战、固定话术，关键词匹配的关联准确率已通过验收；
2. FTS5 需要维护虚拟表与源表同步，增加一类新的不一致风险（与 W3 助教 bug 同类）；
3. C8 的评分优先"交付完成度"与"可验证性"，而不是技术栈先进度；
4. 引入索引层会让"零依赖单文件"的验收优势打折。

## 与前三周的关系

- W1：采用 wechat-cli 的只读原则 → 消除写回风险；
- W2：用 SQLite Property Graph 替换 NetworkX+pickle → 真实替换；
- W3：用 agentskills.io 规范替换自造 skill 格式 → 真实替换；
- W4：评估 FTS5 后维持原方案 → **不是每周都必须换，但每周都必须判断**。

这四周形成了完整的"拿来主义持续执行"证据链：
两次替换、一次部分采用、一次评估后维持。

## 本周结论句

本周我评估了 **SQLite FTS5**，但现有 `challenge_linker` 的关键词方案仍然是最优的，
因为在当前数据规模与固定话术下，索引层带来的复杂度高于收益；
我把它列为 W5 的 A/B 候选项，而不是因为"技术更酷"就替换。
