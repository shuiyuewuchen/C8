# 赵心皓_C8_W2_拿来更新.md

## 本周评估了两个来源

### A. chatlog 的 MCP SSE 集成文档
- **链接**：https://github.com/sjzar/chatlog
- **核心思想**：聊天数据通过本地 HTTP + MCP SSE 暴露，AI 助手按需查询。
- **采用**：transport 与分析解耦的契约思想。
- **丢弃**：常驻服务与 TUI（运维成本）。
- **重构**：把 HTTP API 写为 `cli` 适配器的备选实现说明（`SETUP.md` §3.3），
  上层 `analyze.py` 不需要任何改动即可切换数据源。
- **结论**：**部分采用**。

### B. NetworkX + pickle（材料包推荐的快速原型方案）
- **链接**：https://networkx.org/
- **核心思想**：纯 Python 图结构，序列化到 pickle，原型速度快。
- **采用**：节点/边的领域抽象思路。
- **丢弃**：pickle 作为持久化格式——不可跨语言、不可直接查询、有反序列化风险。
- **重构**：改用 SQLite 两张表实现同构 Property Graph，保留可替换后端接口。
- **结论**：**替换掉原计划**。这是本周真实发生的方案替换，不是嘴上说"持续优化"。

## 评估后维持原方案的记录

按 CHALLENGE.md §5.3，找不到更好方案也要写。本周对 **规则引擎 vs LLM 分类**做了评估：

- 现有规则引擎：准确率 96.4%（内部上界）、零成本、可复现、可解释；
- LLM 分类：理论上对长尾表达更灵活，但引入 API 成本、延迟、不可复现性；
- **结论**：现有方案仍然最优，因为当前消息模式高度结构化（提交有文件名契约、
  通知有固定话术），LLM 的边际收益低于其引入的复杂度。
  W5 留出集评估后如外部准确率低于 65%，再重启 LLM 方案评估。

## 本周结论句

本周我发现了 **chatlog 的 transport 解耦思想与 NetworkX 的持久化短板**，
其中 NetworkX 方案被 SQLite Property Graph **真实替换**，
因为它比我之前的原型方案更好：数据可直接用 sqlite3 查询验证，
且不需要引入 pickle 这种不可审计的持久化格式。
